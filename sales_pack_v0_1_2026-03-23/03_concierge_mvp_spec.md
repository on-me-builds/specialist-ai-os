# Concierge MVP 仕様書 v0

> 取りこぼし患者の見える化 + 呼び戻し運用づくり — 最小検証版
> 目的: 「取りこぼし患者を整理し、LINEで呼びかけると、実際に反応・再来院するか？」を1院で検証する
> 前提: 厳密なデータがない医院でも、現場の感覚と手元情報から始められる構成にする

---

## 前提

- 技術的な自動化は最小限。人間（我々）が手で回す部分が多い
- 予約システムの置き換えはしない
- レセコン連携はしない
- MEO/集患には手を出さない
- 2週間で1サイクル回して判定する

---

## 入力

| 項目 | 提供元 | 形式 |
|------|--------|------|
| 取りこぼし患者リスト | 医院 | CSV / Excel / 手書きメモでもOK |
| 最低必要項目: 患者名、最終来院日（ざっくりでOK）、連絡先（LINE友だちかどうか） | | |
| ※ Type A（データあり）: 予約システムからエクスポート | | |
| ※ Type B（感覚ベース）: スタッフの記憶から10人分を手書き | | |
| LINE配信の協力体制 | 医院 | 初回は医院側で配信。信頼関係構築後に代理配信も相談可 |
| 医院プロフィール | ヒアリング or Product Factory のインテーク | YAML / フォーム回答 |

## 工程

### 手動工程（我々がやること）

| Step | 作業 | 担当 | 所要時間 |
|------|------|------|---------|
| 1 | 取りこぼし患者リストを受領・整理（Type B の場合は手書きメモからリスト化） | 我々 | 30分 |
| 2 | リストから配信対象を選定（10〜30名） | 我々 | 15分 |
| 3 | 呼び戻しメッセージ3パターンを作成 | 我々（AI生成+手動調整） | 1時間 |
| 4 | 医院に文面を確認してもらう | 医院（院長 or 受付） | 翌日まで |
| 5 | 配信用メッセージを医院に納品 → 医院側で LINE配信 | 医院（我々がサポート） | 15分 |
| 6 | 反応を記録（既読/返信/予約確定） | 我々（手動チェック） | 毎日5分×14日 |
| 7 | 予約確定した患者を医院に共有 | 我々 | 随時 |
| 8 | 2週間後にレポート作成 | 我々 | 1時間 |

### 自動化工程（将来移行の候補）

| Step | 現状 | 将来自動化 |
|------|------|----------|
| リスト抽出 | 手動エクスポート | 予約システムAPI or DB連携 |
| メッセージ生成 | AI生成+手動調整 | プロンプト自動実行（Product Factory転用） |
| LINE配信 | 医院側で手動送信 | 代理配信 or n8n → LINE Messaging API |
| 反応記録 | 手動チェック | Webhook → スプレッドシート自動記録 |
| レポート | 手動作成 | 自動集計+テンプレートレポート |

## メッセージパターン（3種）

### パターンA: やさしいリマインド（配信タイミング: 最終来院から2〜4週間後）

```
【{clinic_name}】より

{patient_name}さま、先日は当院にお越しいただきありがとうございました。

その後、お口の調子はいかがでしょうか？
治療の続きについて、ご都合のよいタイミングでご予約いただけますと安心です。

ご予約・ご相談はこちらから：
{booking_url}

ご不明な点がございましたら、お気軽にご連絡ください。
```

### パターンB: 具体的な懸念への言及（配信タイミング: 1〜2ヶ月後）

```
【{clinic_name}】より

{patient_name}さま、お忙しいところ失礼いたします。

前回の治療から少しお時間が経ちましたので、ご案内させていただきました。
お口の状態を一度確認させていただけると安心かと思います。

短いお時間でも大丈夫ですので、
ご都合のよいときにお気軽にご予約ください。

ご予約はこちら：
{booking_url}
```

### パターンC: 最終呼びかけ（配信タイミング: 2〜3ヶ月後）

```
【{clinic_name}】より

{patient_name}さま、ご無沙汰しております。

以前の治療の経過が気になっております。
お忙しいかと思いますが、一度お口の状態を確認させていただければ幸いです。

短い時間の受診でも構いませんので、
ご都合のよい日時をお知らせいただけましたら幸いです。

ご予約：{booking_url}
お電話：{phone}
```

## 確認項目（初回パイロットで見るもの）

> 初回パイロットでは正確な率や売上換算は追わない。見るべきは3つだけ。
> （参照: docs/pilot_success_definition_v0_1.md）

| 優先度 | 確認項目 | 判定基準 |
|:------:|---------|---------|
| **1** | 院長が「続けたい」と言うか | 口頭で確認。振り返り面談で聞く |
| **2** | 呼びかけに1人でも反応があるか | 反応 = 返信・電話・予約のいずれか（既読のみは含めない） |
| **3** | リストの取得と配信が現実的に回ったか | Type A: CSV出力できた / Type B: 手書きでリスト化できた |

### 記録はするが前面に出さない指標

| 指標 | 定義 | 備考 |
|------|------|------|
| 配信数 | メッセージを送った取りこぼし患者数 | 10〜30名が目安 |
| 既読率 | LINE既読 / 配信数 | 記録する。院長には共有するが目標値は設定しない |
| 反応数 | 返信・電話・予約のいずれかがあった件数 | 1件以上が最小成功ライン |
| 再来院数 | 実際に来院した人数 | 2週間では間に合わない可能性あり。追跡は継続 |

> ❌ 推定回収額は初回パイロットでは算出しない。院長に「いくら戻った」とは言わない。

## 成功条件（Go / No-Go）

> 参照: docs/pilot_success_definition_v0_1.md

### Go（有償化を提案する）
以下の **3つすべて** が揃ったとき。
1. 院長が「続けたい」と明言している
2. リストの取得が月次で回せる見込みがある（Type A: CSV出力できた / Type B: 次回はCSV移行の意思あり）
3. 呼びかけに対して1名以上から反応があった（返信・電話・予約のいずれか）

### No-Go（有償化しない・ピボット）
- 配信した全員から反応ゼロ
- 「LINEで連絡されるのは嫌」というクレームが複数
- リストを出す手段がまったくない（手書きでも無理）
- 院長が「この程度なら自分でやる」と判断

### 有償化を見送るケース（Goでも注意）
- 院長が「やれそうだけど自分でやる」→ 我々の介在価値がない
- リストが毎月10人以下 → 母数不足で月額の価値を感じにくい
- LINE友だちが30人未満 → 先にLINE友だち集めが必要
- 院長の本当の課題が別（新患集客・スタッフ問題等）→ 別の提案が必要

---

## やらないこと（明示的な制約）

- ❌ 予約システムの開発・代替
- ❌ 新患獲得（MEO・広告・HP）
- ❌ レセコン連携
- ❌ 患者の個人情報を当方管理のクラウドに保存すること（データは原則として医院管理下の環境で扱う。当方は運用に必要な最小限のみ閲覧。同意範囲は各医院の既存ルールに準じて確認）
- ❌ 大量配信（月200通超はLINE有料プラン要検討）
- ❌ 医療行為の判断を含むメッセージ

---

## ロールバック

テスト期間中に問題が発生した場合：

1. **患者からクレーム** → 即座に当該患者への配信停止。医院と対応協議
2. **LINEブロック多発** → 配信を一時停止。メッセージ内容・頻度を見直し
3. **医院側の運用負荷が高い** → 我々側の作業割合を増やす。それでも厳しければ中止
4. **中断患者リストが不正確** → リスト精査を手動で実施。それでも改善しなければ別の入力方法を検討

**いずれの場合も、予約システム・既存運用への影響はゼロ。** 追加したLINEメッセージを止めるだけで元に戻る。
