# specialist-ai-os 事業計画マスター v0.1

> 作成日: 2026-03-23
> 用途: チーム内部で意思決定と検証方針を揃えるためのマスター文書
> 注意: 本書は外部向けピッチ資料ではない。確定事項と仮説を混同せず、実行判断に使う。

## 1. 事業概要

specialist-ai-os は、歯科医院向けの AI 活用事業として始まったプロジェクトである。現時点での主商品仮説は、FAQ・口コミ返信・求人文・Sales Onepager の4文章生成ではなく、**歯科医院向け中断患者リテンションOS**である。

このサービスが目指すのは、予約システムそのものを置き換えることではない。既存の予約システムや院内オペレーションはそのままに、中断患者や取りこぼし患者を見える化し、戻せそうな患者から呼び戻す運用を作ることである。売るものは文章そのものではなく、患者の再来院を支える運用の仕組みである。

一方で、すでに開発済みの4文章生成は捨てない。これは主商品ではなく、最初の接点を作るための lead magnet、ヒアリング前後の信頼獲得、医院理解の構造化インテーク資産として活用する。

## 2. 背景と問題意識

当初の Product Factory は、医院情報から4つの実務文書を生成する仕組みとして、ローカル実行および n8n simple workflow まで動作確認が済んでいる。つまり、技術的に作れることは確認できた。

ただし、作れることと、事業として勝てることは別である。歯科医院の現場で起きている問題を見直すと、院長やスタッフが本当に困っているのは「文章を作る時間がない」ことだけではない。実際には、「対応したい患者が見えていない」「見えていても誰も運用できない」「忙しくて後回しになり、そのまま放置される」という運用上の詰まりが大きい。

さらに重要なのは、多くの医院で中断患者数やキャンセル率が厳密に把握されていないことである。数字がないため、改善も継続も属人的になりやすい。この前提に立つと、最初に提供すべき価値は高度な最適化ではなく、**見える化と最初の運用化**である。

## 3. なぜ最初の4文章生成だけでは弱いのか

4文章生成は実務上の便利さがある一方で、単体商品としては弱い。理由は明確である。

第一に、代替手段が多い。HP業者、採用業者、汎用テンプレート、ChatGPT の直打ちでも一定水準までは作れてしまう。第二に、継続課金の理由が弱い。一度作ったら終わる性質が強く、毎月払い続ける必然性を作りにくい。第三に、医院側が支払う理由を売上や運用改善に直接結びつけにくい。文章の品質差はあっても、院長にとっての緊急度や投資判断にはなりにくい。

つまり、4文章生成は「価値がない」のではなく、「主商品に向かない」。この位置づけの整理が今回のピボットの起点である。以後は、4文章生成を主戦場に据えず、あくまで主商品への入口として扱う。

## 4. 現在のピボット内容

今回のピボットで変わったのは、何を主商品として売るかである。文章生成中心のプロダクト仮説から、既存患者の取りこぼしを減らす運用OS仮説へ軸を移した。

このピボットで確定していることは3つある。1つ目は、**最初の対象を歯科に限定する**こと。将来的な横展開はあり得るが、今はやらない。2つ目は、**売り物を成果物ではなく運用に置く**こと。3つ目は、**いきなり SaaS を作らず concierge MVP で始める**こと。現時点では、プロダクトの完成度よりも、現場で本当に回るかを先に見極める。

変わらないものもある。医院理解を素早く構造化すること、現場で使われる文面を整えること、n8n やテンプレートを使って少人数で素早く回すことは引き続き強みとして使う。

## 5. 主商品仮説の定義

主商品名の仮称は**中断患者リテンションOS**である。

定義は次の通りである。既存の予約システムや院内運用はそのままに、中断患者・取りこぼし患者を見える化し、戻せそうな患者から優先順位をつけて呼び戻し、反応記録と再予約導線までを継続運用できるようにするサービスである。

ここで重要なのは、「自動配信ツール」ではなく「運用OS」と定義している点である。価値の中心は、単にメッセージを送れることではない。誰に、どの順番で、どの文面を、どの頻度で送り、その結果をどう記録し、次回の対応にどうつなげるかまでを運用として定着させることにある。

## 6. 対象顧客（どんな歯科医院か）

現時点の第一対象は、既存患者が一定数おり、予約システムを使っているが、中断患者対応が属人的または未着手の歯科医院である。院長が「気にはなっているが、手が回っていない」と感じている医院が最も有力である。

より具体的には、以下の特徴を持つ医院を優先する。

- 中断患者や失注患者が発生している感覚はあるが、厳密な数は把握できていない
- 予約システム、Excel、CSV、紙台帳など何らかの形で患者情報にアクセスできる
- LINE、SMS、メールのいずれかで患者連絡の導線を持つ、または持てる
- 院長または受付責任者が、現状運用に課題を認識している
- 新患集客だけでなく、既存患者の取りこぼしにも関心がある

MVP 上は、Type A と Type B の2ルートを想定する。Type A は予約履歴や CSV を出せる医院、Type B は数字が弱く、まず2週間の手動記録や見える化シートから入る医院である。両方を対象にするが、初期学習効率の観点では Type A の方が立ち上がりは速い可能性が高い。ここは現時点では仮説である。

## 7. 顧客の痛み（現場知見を含む）

歯科医院の現場で起きている痛みは、単に「集患が足りない」ではない。むしろ、すでに接点があった患者を取りこぼしていることに対して、何も打ち手を持てていないことにある。

典型的な痛みは次の通りである。

- 治療途中で来なくなった患者がどれくらいいるかわからない
- リストがあっても、誰が対応するか決まっていない
- 電話フォローは負担が重く、継続しない
- LINE で連絡したいが、文面や順番に自信がない
- 送った後の反応記録が残らず、次の改善につながらない
- 院長は問題意識を持っていても、受付・スタッフに落ちる運用になっていない

ここで重要な現場知見は、**多くの医院が精緻な数字を持っていない**ことである。したがって、初期フェーズでは「キャンセル率を何ポイント改善するか」のような精密 KPI よりも、「まず対象患者を特定できるか」「運用が回るか」「院長が価値を感じるか」が先に来る。

## 8. 提供価値

本サービスの提供価値は、単一ではない。現時点では、少なくとも次の3層で価値を出す必要がある。

1つ目は、**見える化の価値**である。中断患者候補を整理し、感覚でしか語れなかった問題を「対応可能なリスト」に変える。多くの医院にとって、ここだけでも価値がある。

2つ目は、**運用化の価値**である。誰に何を送るか、誰が送るか、どう記録するかを決めることで、思いつきの対応を継続可能な運用に変える。ここが文章生成単体との大きな違いである。

3つ目は、**再来院の価値**である。実際に患者が戻り、再予約が入り、取りこぼしの回収につながる。将来的に最も大きい価値はここにあるが、初期提供では必ずしもこの層だけを約束しない。見える化と運用化が先に立ち、その上で再来院成果を検証していく。

## 9. 提供内容（初期MVP）

初期提供は concierge MVP とする。つまり、いきなりソフトウェアを全面提供するのではなく、半手動で実際の運用を作り、価値検証を優先する。

初期 MVP の提供内容は以下を想定する。

- 中断患者候補の整理
- 呼び戻し対象の優先順位づけ
- LINE / SMS / メール等の文面作成
- 医院側配信を前提にした安全な運用設計
- 反応記録シートまたは簡易ログ設計
- 再予約導線の整理
- 週次または月次の簡易振り返り

初期スコープで明確にしておくべき前提もある。**こちらが医院の LINE 公式アカウント管理画面に入ることは初回前提にしない。** 基本形は「こちらが対象整理と文面作成を行い、医院側が送信する」である。信頼関係が築けたあとに運用代行範囲を広げる可能性はあるが、それは初期条件ではない。

Type A と Type B では進め方が異なる。Type A は既存データから対象抽出を行い、そのまま2週間前後のパイロットに進む。Type B は、まず2週間の簡易記録や見える化シートで現状把握を行い、その後に呼び戻しテストに進む。初期 MVP は、この2ルートを回せる設計にしておく。

## 10. 4文章生成の位置づけ

FAQ・口コミ返信・求人文・Sales Onepager の4文章生成は、今後も資産として使う。ただし、その役割は主商品ではない。

位置づけは以下の3つである。第一に、front-end offer としての役割である。無料または低額で価値を渡し、最初の接点を作る。第二に、初回お土産としての役割である。面談前後に具体物を渡すことで信頼を作る。第三に、顧客理解インテーク装置としての役割である。医院情報、訴求軸、トーン、採用・集患・運用課題を構造化データとして取得できるため、主商品側のオンボーディングにも使える。

重要なのは、4文章生成を単体商品として育てるのではなく、主商品への導線と設定資産として使うことである。ここを曖昧にすると、再び「便利だが弱い商品」に時間を使うことになる。

## 11. 競争環境の見立て

現時点の見立てでは、歯科向け市場には crowded な領域と、まだ運用が弱い under-served な領域がある。

crowded な領域は、予約システムそのもの、単純なリマインド通知、MEO / 口コミ運用の主戦場、求人媒体そのもの、FAQ や文章テンプレ生成単体である。これらはすでにプレイヤーが多く、機能比較や価格比較に引き込まれやすい。

一方で、狙うべき領域は、中断患者の呼び戻し運用、リコール最適化、採用後の定着・教育、既存システムの上に乗る運用改善層である。この領域では、機能は一部あっても、実際に回る運用として提供されていないケースが多い。

当社の立ち位置は明確である。予約台帳やレセコンを置き換えない。既存システムの上に乗る。ツールを渡して終わるのではなく、リスト化、優先順位づけ、配信、反応、再予約までの運用ループを作ることを価値にする。

ただし、予約システム事業者が今後この領域に深く入ってくるリスクはある。そのため、初期は機能競争ではなく、現場導入の速さと運用実装力で先に学習を進める必要がある。

## 12. 売り方 / 導線仮説

最初の販売は X 単独では成立しない前提で考える。X は売る場所ではなく、問題認識を作り、信頼を形成し、面談の入口を作る distribution channel である。

現時点の導線仮説は以下である。知人・紹介・既存接点、または X などでの問題提起から接点を作る。次に、院長ヒアリングシートを用いて pain、現状運用、データ取得可否、支払い意欲を確認する。そのうえで、1枚営業資料とパイロット提案文を使い、2週間前後の小さなテスト運用を提案する。価値が確認できた場合に有償化へ進む。

すでに営業・検証資産として、院長ヒアリングシート、retention onepager、concierge MVP 仕様書、パイロット提案文は整っている。したがって、今やるべきことは営業資料を増やすことではなく、実際に会話し、検証し、導線の歩留まりを確認することである。

## 13. ビジネスモデル仮説

現時点のビジネスモデル仮説は、**無料または低額の front-end offer → 無料または低額のパイロット → 月額運用支援**の流れである。

4文章生成は front-end offer として使う。パイロットは導入障壁を下げるため、無料または低額を想定する。本導入は月額 3〜5万円帯を初期仮説とするが、これはまだ確定ではない。支払われる対象は、文章の納品物ではなく、中断患者の見える化と呼び戻し運用を継続する支援である。

このモデルが成立する条件は、少なくとも次の3つである。第一に、院長が「この運用は続けたい」と感じること。第二に、月次の運用負荷が人手で回せる範囲に収まること。第三に、再予約や反応改善を、定量または半定量で説明できること。

価格の細部、初期費用の有無、成果報酬の扱い、従量課金の要否は未確定である。現段階では、価格表を詰めるよりも、誰が何に対していくらなら払うかをヒアリングとパイロットで確認する方が先である。

## 14. 初期KPI / 検証項目

初期 KPI は、精密な経営ダッシュボードではなく、現場で事業成立性を判断するための指標として置く。多くの医院で基礎数字が弱いため、最初から厳密 KPI に寄せすぎない。

見るべき項目は以下である。

- 中断患者リストを出せるか
- 実際に対象患者を特定できるか
- 医院側が配信を実行できるか
- 既読率
- 返信率
- 再予約率
- 院長が継続したいと感じるか
- 月額を払う意思があるか

加えて、定量以前の重要シグナルとして、「これまで見えていなかった問題が見えるようになったか」「院内で誰が対応するかが決まったか」「院長が放置コストを実感したか」も評価する。初期フェーズでは、これらの定性情報も重要な経営判断材料である。

## 15. 今やらないこと

この事業で今やらないことは明確に固定する。

- 予約システムそのものの開発
- レセコン置き換え
- MEO / 口コミ運用を主戦場にすること
- FAQ や求人文の単体商品化
- いきなり全自動 SaaS 化
- 他業種への横展開
- 大規模な外注体制やコンサル色の強い展開
- 初期段階から医院アカウントへ深く入り込む運用代行

これらをやらない理由は、価値がないからではない。焦点がぶれ、学習速度が落ち、主商品仮説の検証が遅れるからである。今は一本目の勝ち筋を歯科で通すことが最優先である。

## 16. リスクと前提条件

最大のリスクは、データ取得の壁である。中断患者リストが出せない医院では、そもそも呼び戻し運用に入れない。この前提に対しては、Type B ルートとして手動記録や見える化シートから始める設計が必要になる。

次に、配信実行が医院側依存になるリスクがある。初期は医院側送信を前提にするため、こちらがどれだけ準備しても、医院が送らなければ検証は進まない。したがって、初回パイロットでは対象人数を絞り、送信までの工程を短くし、実行責任者を明確にする必要がある。

また、患者連絡には個人情報やコミュニケーション上の配慮が伴う。初期は医院管理下のアカウント、シート、配信導線を前提にし、文面は医院確認のうえで送る運用を基本とする。法令やガイドラインへの配慮を欠いた拡張運用は行わない。

さらに、競争リスクもある。予約システムベンダーがこの領域を深く取りに来れば差別化は難しくなる。そのため、初期は SaaS の完成度ではなく、現場での実装速度と運用知見の蓄積を優先する。

最後に、concierge MVP は学習速度を上げる一方で、人手依存にもなる。どこまで手でやるか、どこから共通化するかの境界を意識しないと、単なる受託運用に寄るリスクがある。

## 17. 今後2〜4週間のアクション

直近2〜4週間では、資料作成よりも検証を優先する。やるべきことは次の通りである。

1. 院長ヒアリングを5件以上行い、中断患者対応の現状、データ取得可否、支払い意欲を確認する。
2. Type A と Type B の医院を少なくとも各1件ずつ見つけ、どちらの立ち上がりが現実的かを比べる。
3. Type A 候補があれば、中断患者10〜30名規模の2週間パイロットを実施する。
4. Type B 候補があれば、まず2週間の見える化シート運用を回し、その後に呼び戻しテストへ移れるかを確認する。
5. パイロット中の記録項目を固定し、既読率、返信率、再予約率、院長所感を同じフォーマットで残す。
6. 既存の営業キットを実戦投入し、面談から提案、パイロット化までの歩留まりを把握する。
7. 有償化する場合の最小提供パッケージを定義し、どこまでが標準範囲かを明文化する。

この期間の目的は、売上最大化ではない。主商品仮説が現場で成立するか、どこで詰まるかを具体的に知ることである。

## 18. 現時点で未確定な論点

以下は、まだ決め切っていない論点である。

- 最初に最も刺さる歯科医院セグメントはどこか
- Type A と Type B のどちらを主導線にすべきか
- 配信チャネルの第一優先は LINE でよいか。SMS やメールの方が現実的な医院はどれくらいあるか
- 2週間パイロットの成功基準をどこに置くか
- 本導入時の標準提供範囲をどこまでにするか
- 月額 3〜5万円帯が現実的に受け入れられるか
- 4文章生成を無料にするか低額にするか
- どのタイミングで手動運用をシステム化するか

未確定論点があること自体は問題ではない。問題なのは、未確定のまま走ることではなく、未確定なのに確定済みのように振る舞うことである。ここは検証項目として扱う。
