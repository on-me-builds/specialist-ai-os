# specialist-ai-os
歯科医院向け 中断患者リテンションOS
内部共有デック v0.1
2026-03-23

---

# 今回の結論
- 4文章生成は主商品ではない
- 主商品仮説は中断患者リテンションOSである
- 最初の対象は歯科のみとする
- 売り物は文章ではなく運用である
- いきなり SaaS に行かず concierge MVP で始める

---

# なぜ4文章生成だけでは弱いのか
- FAQ、口コミ返信、求人文、onepager は代替が多い
- HP業者、採用業者、テンプレ、ChatGPT 直打ちでも一定水準まで作れてしまう
- 一度作ると終わりやすく、継続課金の理由が弱い
- 院長の強い痛みや売上回復に直結しにくい
- 価値はあるが、主商品には向かない

---

# 現場で起きている本当の問題
- 取りこぼし患者が何人いるか見えていない
- 見えていても誰が追うか決まっていない
- 電話だけでは継続しない
- 送った後の反応記録が残らない
- 忙しさの中で放置される
- 数字が弱くても、現場の痛みは強い

---

# 主商品の定義
予約システムはそのままで、取りこぼし患者を見える化し、戻せそうな人から呼び戻す運用を作るサービス

- 既存システムを置き換えない
- 中断患者や失注患者の候補を整理する
- 戻せそうな人から優先順位をつける
- 文面、反応記録、再予約導線まで運用化する

---

# 誰に売るか
- 既存患者が一定数いる歯科医院
- 予約システム、Excel、CSV、紙台帳のどれかで患者情報に触れられる
- 中断患者対応が属人的または未着手
- LINE、SMS、メール、電話のいずれかで連絡可能
- 院長か受付責任者が課題を認識している

---

# Type A / Type B の2ルート
- Type A: 予約履歴や CSV があり、そのまま対象候補を出せる医院
- Type B: 数字は弱いが、中断患者がいる感覚はある医院
- Type A はそのまま小規模パイロットに進みやすい
- Type B は2週間の見える化シートや手動整理から始める
- どちらが先に立ち上がるかは現時点では仮説

---

# どこで勝つか
- crowded: 予約システムそのもの、単純なリマインド、MEO、文章生成単体
- under-served: 中断患者の呼び戻し運用、リコール最適化、既存システム上の運用改善
- 予約台帳やレセコンを置き換えない
- ツール提供ではなく、運用ループを作る
- 現場導入の速さと実装力で先に学習する

---

# MVP の進め方
- 初期は「こちらが対象整理と文面作成、医院側が送信」を基本形にする
- Type A は対象抽出から2週間パイロットへ進む
- Type B は見える化シートで現状整理し、その後に呼び戻しテストへ進む
- 反応記録と再予約導線を簡易に設計する
- 週次または月次で振り返る

---

# ビジネスモデル仮説
- 4文章生成は front-end offer とインテーク資産として使う
- パイロットは無料または低額で導入障壁を下げる
- 本導入の初期仮説は月額 3〜5万円帯
- 支払い対象は納品物ではなく運用継続支援
- 有償化の条件は、続けたい感覚、実行負荷、反応の説明可能性

---

# 最初に検証すること
- 中断患者リストを出せるか
- 実際に対象患者を拾えるか
- 医院側が配信を実行できるか
- 反応があるか
- 院長が継続したいと思うか
- 月額を払う意思があるか
- Type A / Type B のどちらが先に立ち上がるか

---

# 今やらないこと
- 予約システムそのものの開発
- レセコン置き換え
- MEO や口コミ運用を主戦場にすること
- FAQ や求人文の単体商品化
- いきなり全自動 SaaS 化
- 他業種への横展開
- 大規模な外注体制

---

# 直近2〜4週間のアクション
- 院長ヒアリングを5件以上実施する
- Type A と Type B の候補医院を各1件以上見つける
- Type A は10〜30名規模の小規模パイロットを走らせる
- Type B は見える化シート運用を試す
- 記録項目を固定し、歩留まりを揃えて残す
- 有償化時の最小提供範囲を定義する
